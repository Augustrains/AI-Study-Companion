# 算法接入与掌握度协议

本文面向算法和后端同事，说明如何在不读取参考答案、不绕过审核状态、不重复消费证据的前提下接入选题、掌握度和复习调度算法。

## 1. 当前可直接使用的能力

数据库提供五个只读算法视图和一个受控写入函数：

| 对象 | 用途 | 是否含答案 |
|---|---|---|
| `algorithm_knowledge_catalog` | 读取 50 个正式激活知识点及课程层级 | 否 |
| `algorithm_question_catalog` | 读取已发布、已映射、评测规格已发布的题目 | 否 |
| `algorithm_prerequisite_graph` | 读取已审核发布的前置关系 | 否 |
| `algorithm_evidence_feed` | 读取可用于掌握度更新且尚可追踪处理状态的证据 | 否 |
| `algorithm_learner_state` | 读取当前掌握度、记忆状态和下次复习时间 | 否 |
| `apply_mastery_update(...)` | 幂等、带版本锁地写入掌握度历史和当前状态 | 不接收答案 |

算法数据库账号继承 `app_learning_algorithm`。该角色不能读取 `learning_item_versions.answer_data`、`item_options.is_correct`、隐藏测试，也不能直接修改掌握度表。

## 2. 两个互相独立的学习维度

### 2.1 知识掌握等级

`mastery_level` 取值：

| 等级 | 含义 |
|---|---|
| `未评测` | 没有足够有效证据 |
| `不会` | 当前表现明显低于基本理解要求 |
| `了解` | 能识别或解释部分概念，但不稳定 |
| `熟悉` | 能正确处理大部分任务，但尚未满足长期掌握门槛 |
| `掌握` | 分数门槛、重复独立作答和延迟复测门槛同时满足 |

### 2.2 记忆状态

`memory_status` 取值：

| 状态 | 含义 |
|---|---|
| `未验证` | 还没有独立成功证据 |
| `首次验证` | 已有独立成功，但还没有延迟复测成功 |
| `延迟复测通过` | 至少一次间隔后的主动回忆成功 |
| `稳定保持` | 多次延迟复测成功且当前没有延迟失败 |

这两个维度不能合并。学生可能“当前会做”，但尚未证明数天后仍能回忆；这时掌握等级可为 `熟悉`，记忆状态仍是 `首次验证`。

## 3. 证据进入规则

只有同时满足以下条件的 `assessment_evidence` 才会出现在 `algorithm_evidence_feed`：

- `evidence_strength` 不是 `none`；
- `score` 在 0 到 1 之间且非空；
- 已明确 `knowledge_point_id`；
- 已明确 `task_mode`，或可从 assessment assignment 推导；
- 数据库约束保证提示次数、重试次数和耗时不为负数。

证据强度：

| 值 | 典型来源 | 建议用途 |
|---|---|---|
| `direct` | 已审核 Quiz 精确评分 | 直接更新掌握度 |
| `strong` | 通过已审核自动测试的代码或 Notebook | 高权重更新 |
| `auxiliary` | Rubric、项目表现或人工观察 | 辅助更新，不单独判定掌握 |
| `none` | 未配置评测或只有浏览行为 | 不进入掌握度更新 |

后端生成证据时必须同时写入 `task_mode`、`is_independent`、`is_delayed_retrieval` 和 `scheduled_interval_days`。仅把一次正确作答标为 `掌握`是不允许的。

## 4. 推荐处理流程

```text
评分服务完成评测
  → 写 evaluation_results
  → 写 assessment_evidence
  → 算法读取 algorithm_evidence_feed 中 processed_at 为空的事件
  → 算法读取 algorithm_learner_state 当前版本
  → 计算新的掌握等级、记忆状态和复习时间
  → 调用 apply_mastery_update(...)
  → 数据库校验证据归属、证据唯一性和 expectedStateVersion
  → 追加 learner_mastery_history
  → 更新 learner_mastery_current
  → 标记 mastery_evidence_processing
```

同一批证据只能处理一次。重复调用同一个 `updateId` 会返回原 `stateVersion`；用新 `updateId` 重复消费已处理证据会返回冲突。并发更新必须携带读取时的 `expectedStateVersion`。

## 5. 参考规则算法

`backend/algorithms/mastery_rules.py` 是可运行、可替换的规则版参考实现。它提供：

- 按证据强度和任务模式加权；
- 对提示和重试降权；
- 错误证据可降低过高估计；
- “掌握”必须至少累计 3 次独立成功和 1 次延迟复测成功；
- 独立计算记忆状态、稳定天数和下次复习时间；
- 输出 `reasonCodes`、算法名称和版本，便于解释与回放。

调用示例：

```bash
python3 backend/algorithms/mastery_rules.py \
  --input interfaces/examples/mastery-update-input.json
```

输入示例见 `interfaces/examples/mastery-update-input.json`，输出示例见 `interfaces/examples/mastery-update-output.json`。后续可以用 BKT、IRT、DKT 或其他模型替换计算部分，但数据库写入协议和安全边界保持不变。

## 6. HTTP 接口

OpenAPI 3.1 契约位于 `openapi-question-bank.yaml`，与掌握度相关的接口包括：

- `GET /learners/me/knowledge-status`
- `GET /learners/me/knowledge-status/{knowledgePointId}`
- `GET /learners/me/mastery-history`
- `GET /knowledge-points/{knowledgePointId}/prerequisites`
- `GET /internal/mastery/evidence-events`
- `POST /internal/mastery/updates`

学生接口只能从 `student_knowledge_status_safe` 和 `student_mastery_history_safe` 读取，并在事务中设置服务端验证的 `app.current_user_id`。内部算法接口使用独立服务身份，不能复用浏览器或学生数据库凭据。

## 7. 知识点与题目选择

生产算法只能使用正式表：

```text
item_knowledge_maps       正式题目—知识点映射
knowledge_edges           正式前置关系
algorithm_question_catalog 仅已发布可用题目
```

以下对象只是人工审核工作区，不能作为生产真值：

```text
item_knowledge_map_candidates
knowledge_edge_candidates
quiz_review.csv
practice_knowledge_mapping_candidates.csv
```

当前 301 道 Quiz 和 122 条实践素材都有映射候选，但尚未人工批准，因此正式算法题目目录初始为空。这是发布安全状态，不是数据缺失。

## 8. 前置关系审核发布

教研在 `backend/generated/knowledge_edge_candidates.csv` 中确认方向，设置 `review_status=approved` 并填写 `reviewer_id`。先执行审计：

```bash
python3 backend/scripts/prerequisite_release.py \
  --review-csv backend/generated/knowledge_edge_candidates.csv \
  --taxonomy backend/generated/knowledge_taxonomy.json \
  --report backend/generated/prerequisite_readiness_report.json
```

审核完成后增加 `--emit-sql`、`--batch-id`、`--batch-name`、`--actor` 生成发布 SQL。SQL 只调用 `publish_knowledge_edge_batch(...)`；数据库会在同一事务中再次核对候选值并检测环路。任何一条边产生环路，整批回滚。

## 9. 后端实现检查清单

- 为学生、评分、算法、审核和发布使用不同数据库登录角色；
- 每个学生事务设置并在事务结束后自动清除 `app.current_user_id`；
- 所有 POST 接口落实 `Idempotency-Key`；
- 评分与证据写入同一业务事务，或使用可靠事件/outbox；
- 算法更新只调用 `apply_mastery_update(...)`；
- 409 映射到幂等冲突或状态版本冲突，422 映射到证据/负载校验失败；
- 日志记录 `updateId`、`stateVersion`、算法版本和原因码，不记录答案；
- 上线前执行全部静态测试和 PostgreSQL 16 集成测试。

## 10. 仍需人工或业务系统配合

- 教研审核 301 道 Quiz 的答案、映射、中文翻译和解析；
- 教研审核 122 条实践素材映射与 48 条前置关系；
- 为代码和 Notebook 任务编写沙箱、测试用例或 Rubric；
- 现有后端按 OpenAPI 实现 HTTP 路由、JWT 鉴权和业务事务；
- 使用真实学生数据校准阈值、证据权重和复习间隔。

数据库包已经提供这些工作的安全入口，但不会伪造人工审核结论，也不会替代你们现有后端的鉴权和网络服务。
